# Детектор канцеляризмов

Гибридная (rule-based + LLM) система для поиска трёх видов канцеляризмов в русскоязычном тексте:

1. **Цепочки отглагольных существительных** (2 и более подряд, например "проведение оценки эксплуатации")
2. **"Слабые" (вспомогательные/связочные) глаголы** (например "осуществлять замену" → "заменять")
3. **Заимствования**, употреблённые как канцеляризмы (с учётом контекста и белого списка устоявшихся терминов)

Для каждой найденной конструкции система предлагает 1–2 варианта замены.

## Архитектура

Для всех трёх типов используется общий подход: быстрый rule-based фильтр находит кандидатов, а LLM подтверждает находку и предлагает замену с учётом контекста.

```
project/
├── main.py                     # точка входа
├── config.yaml                 # настройки модели, пути к данным и промптам
├── requirements.txt
│
├── core/
│   ├── preprocessor.py         # токенизация, лемматизация, POS-теггинг (Natasha)
│   ├── white_list.py           # слова-исключения, которые не считаются канцеляризмами
│   └── postprocessor.py        # разбор и нормализация ответов LLM (JSON/фолбэки)
│
├── detectors/
│   ├── base_detector.py        # общий интерфейс детектора
│   ├── verbal_nouns.py         # тип 1
│   ├── weak_verbs.py           # тип 2
│   └── borrowings.py           # тип 3
│
├── llm/
│   └── client.py                # обёртка над Hugging Face Inference Router (OpenAI-совместимый API)
│
├── data/
│   ├── white_list.txt
│   ├── weak_verbs.txt
│   ├── foreign_words.txt
│   ├── verbal_nouns_prompt.txt
│   ├── weak_verbs_prompt.txt
│   └── borrowings_prompt.txt
│
└── evaluation/
    ├── benchmark_dataset.json   # тестовый набор текстов с эталонной разметкой
    ├── evaluate_dataset.py      # прогон пайплайна на всём датасете + подсчёт метрик
    └── metrics.py                # сопоставление предсказаний с эталоном (по леммам и типу)
```

## Установка

```bash
pip install -r requirements.txt
```

Понадобится токен Hugging Face с разрешением **"Make calls to Inference Providers"** (Settings → Access Tokens → создать fine-grained токен). Впишите его в `config.yaml`:

```yaml
llm:
  model: "Qwen/Qwen3-Coder-480B-A35B-Instruct"
  temperature: 0.1
  max_tokens: 1000
  api_key: "hf_..."
```

## Использование

```bash
python main.py
```
Введите или вставьте текст, затем нажмите Enter на пустой строке для запуска анализа.

Либо передайте текст файлом:
```bash
python main.py path/to/text.txt
```

## Оценка качества (бенчмарк)

```bash
python evaluation/evaluate_dataset.py
```

Прогоняет пайплайн на всех текстах из `benchmark_dataset.json` и выводит точность в целом и по каждому из трёх типов канцеляризмов.

### Текущие результаты

| Тип канцеляризма | Ожидалось | Найдено верно | Точность |
|---|---|---|---|
| Отглагольные существительные | 36 | 21 | 58.33% |
| Слабые глаголы | 49 | 32 | 65.31% |
| Заимствования | 27 | 19 | 70.37% |
| **Итого** | **112** | **72** | **64.29%** |

### Известные ограничения

- **Отглагольные существительные** детектируются только как цепочки из 2+ слов подряд (согласно ТЗ) — одиночные канцелярские существительные вне цепочки не ловятся принципиально, это архитектурное решение, а не баг.
- Rule-based фильтр для отглагольных существительных спроектирован с избытком recall (например, суффикс "-ка" ловит и неотглагольные слова вроде "сумка") — расчёт на то, что финальную фильтрацию по смыслу делает LLM-этап; часть ложных срабатываний — цена этого компромисса.
- Граница цепочки может обрываться на цифрах/датах внутри фразы (например, в датах или номерах созывов) — известное ограничение токенизации.
- Точность заимствований напрямую зависит от полноты словаря `data/foreign_words.txt` — слово, отсутствующее в словаре, не будет найдено независимо от контекста.
- Три детектора работают полностью независимо; итоговая точность ниже точности любого отдельного детектора, так как находка должна совпасть с эталоном одновременно по типу и по содержанию.

## Известные ограничения по LLM-провайдеру

Проект использует Hugging Face Inference Router (`router.huggingface.co`), который проксирует запросы к сторонним inference-провайдерам. Возможные проблемы:
- бесплатный месячный лимит кредитов ограничен и общий для всех моделей/виджетов на аккаунте;
- не все модели из каталога Hugging Face фактически обслуживаются провайдерами в любой момент времени (ошибка `model_not_supported`);
- reasoning-модели (например, DeepSeek-R1) могут не укладываться в `max_tokens` и обрывать ответ посреди блока `<think>` — для этой задачи рекомендуются обычные instruct-модели без встроенного reasoning.

При недоступности LLM все три детектора откатываются на встроенные rule-based эвристики и заготовленные словари замен (`FALLBACK_BY_LEMMA` и аналогичные), так что пайплайн не падает полностью даже без доступа к API.
